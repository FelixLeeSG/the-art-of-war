# /battle-plan — 庙算：战略规划

> 「夫未战而庙算胜者，得算多也；未战而庙算不胜者，得算少也。多算胜，少算不胜，而况于无算乎？」 —— 孙子兵法·始计篇

## Skill 定义

**名称**：battle-plan（庙算）
**触发**：`/battle-plan <任务描述>`
**定位**：在动手编码之前，像古代将领庙堂算计一样，系统性地评估任务并制定作战方案。

## 核心兵法原则

### 始计篇 — 五事七计
孙子以「道、天、地、将、法」五事评估战局。映射到软件工程：

| 五事 | 软件工程含义 | 评估要点 |
|------|-------------|---------|
| **道** | 目标对齐 | 这个任务是否与产品目标一致？用户真正需要什么？ |
| **天** | 时机与约束 | 截止日期？上下游依赖的时间窗口？ |
| **地** | 技术地形 | 代码库现状？技术栈限制？运行环境？ |
| **将** | 团队能力 | 谁来实现？熟悉度如何？需要什么技能？ |
| **法** | 工程规范 | 编码规范？测试要求？CI/CD 流程？ |

### 谋攻篇 — 攻击等级
选择最优实现策略，优先级从高到低：

1. **伐谋**（最上）— 用配置/设置解决，不写代码
2. **伐交**（其次）— 用现有库/API/服务解决
3. **伐兵**（再次）— 修改现有代码解决
4. **攻城**（最下）— 从零开始实现新系统

## 工作流程

```
输入：任务描述/需求

步骤一：侦察（知己知彼）
  - 分析需求的真实意图
  - 扫描相关代码库区域
  - 识别现有可复用的资源

步骤二：五事评估
  - 目标明确度 ✓/✗
  - 时间约束评估
  - 技术可行性分析
  - 能力匹配度
  - 规范约束确认

步骤三：选择攻击等级
  - 能否不写代码就解决？（伐谋）
  - 能否用现有工具/库？（伐交）
  - 能否最小改动现有代码？（伐兵）
  - 是否必须新建？（攻城）

步骤四：制定作战计划
  - 分解子任务
  - 确定执行顺序
  - 识别风险点与备选方案
  - 预估复杂度

输出：结构化作战计划
```

## 输出格式

```markdown
## 🏛 庙算报告

### 战情分析
[需求的本质是什么]

### 五事评估
- 道（目标）：[评估]
- 天（时机）：[评估]
- 地（地形）：[评估]
- 将（能力）：[评估]
- 法（规范）：[评估]

1. [步骤一]
2. [步骤二]
...

### 风险与备策
- 风险：[描述] → 备策：[应对]

### 胜算评估
[整体可行性判断]
```

## 示例场景

**输入**：`/battle-plan 给用户管理模块添加角色权限功能`

**庙算过程**：
- 侦察：发现已有 RBAC 库在 package.json 中但未使用 → **伐交**策略可行
- 五事：目标明确、时间充裕、代码库有基础、团队熟悉、有测试规范
- 决策：不从零实现权限系统（避免攻城），而是集成已有的 RBAC 库（伐交）
- 计划：1) 配置 RBAC 库 → 2) 定义角色模型 → 3) 添加中间件 → 4) 写测试
